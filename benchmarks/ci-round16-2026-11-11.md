# Reusing a previous planner graph, November 11, 2026

Measured on Linux amd64 with Go 1.26.5. Baseline `812a308` is the final tree of
PR #22; implementation `0d73aa6` adds the opt-in `previousPlan` argument. The
subsequent test expansion covers compact archives and early cutoff without
changing the measured implementation.
[Raw results and validation](ci-round16-2026-11-11.json) accompany this report.

## Why reuse a previous graph

A diagnostic prepared-UPM planner evaluated its graph in read-only iets mode in
0.090–0.095 s, while ordinary evaluation plus registration took 1.027–1.041 s.
Both modes produced the same derivation path in a strict recursive sandbox.
This fixed-order diagnostic isolates a lead; it is not an optimization benchmark.

Passing a previous `.planner` output as a declared input makes that graph's
closure visible to the restricted store from the start. Discovery still reads
the current source and creates its current recipes. The evaluator can skip
registration of sources and derivations that have exactly the same store paths.
Changed inputs produce new recipes as usual. This works with either nested
Nix or iets, and adds no fallback or exception to sandbox visibility.

## Warm CI timings

Seven alternating trials per scenario, plus excluded warmups, use
`scripts/benchmark-ci.py`. Each unique forwarding name forces fresh planning.
Tools, compiled Go package outputs, and the previous plan are already local.
Totals include outer Nix evaluation and realization, nested planning, and output
forwarding. Sandboxing is enabled without fallback; IFD, remote cache queries,
and forced substitutions are disabled. Build scheduling uses four jobs and two
cores per job. Nested static iets is PR #3 revision
`69883a64bfb0d9a95dce253dae304878e07b076e`, with one evaluator worker, both evaluator
caches disabled, and classic fallback disabled.

All before/after trials produce identical Go outputs for the selected current
source. Both nested evaluators also agree. The saved plan remains from the
original source in the edited scenarios: the fixture changes an embedded asset,
and UPM adds a comment to `cmd/upm/main.go`. Both edits produce different output
store paths from the unedited source, while fresh and seeded planning agree.
The changed fixture also runs with the expected new embedded data. Edited
compilation is warmed before timing; this table isolates planning cost.

UPM is revision `35a76c282507fb942445c0ee98427b3d1ef772bc`, package `./cmd/upm`.
Proxy mode extracts the pinned module proxy for each plan. Prepared mode shares
an existing immutable module cache. These measurements do not include network
transfer, cold compilation, or the first construction of the prior plan.

## Cache payload tradeoff

The previous graph becomes a planner input, including its source snapshots and
raw derivation closure. Local binary caches compressed with zstd level 3 measure:

| Workload, nested iets | Input paths before / after | NAR bytes before / after | Compressed bytes before / after |
|---|---:|---:|---:|
| Fixture | 909 / 993 | 235,726,160 / 241,403,600 | 61,773,471 / 63,410,681 |
| Prepared UPM | 910 / 1,592 | 1,286,523,000 / 1,351,699,808 | 215,792,491 / 228,057,584 |

This adds **1.64 MB compressed and 84 paths** for the fixture, or **12.27 MB and
682 paths** for UPM. Payloads were measured with a prototype using the existing
`runtimeInputs` parameter; exact input-source and input-derivation sets were
then verified identical for the public `previousPlan` argument. The JSON records
both planner paths and the verification.

This is a warm-store optimization with an explicit cold-store cost. Fetching
hundreds of additional cache objects can offset the saved planning time on a
fresh worker. `previousPlan` therefore defaults to `null`. It is useful when CI
retains or preloads the prior graph. New plan output closures exclude the old
plan root, so publishing successive outputs does not copy a chain of prior plans.
Compiled outputs and their worker inputs are unchanged.

## Use and reproduction

Supply an earlier result's `.planner`, or an already restored store path, as
`previousPlan` in `nix/dynamic.nix` or `lib.mkGoPackage`. When passing a derivation,
Nix builds its output if necessary; restoring a known prior plan avoids running
old discovery again. Publish the planner output separately from the executable:

```sh
plan=$(nix build .#my-package.planner --no-link --print-out-paths)
nix copy --to "$CACHE" "$plan"
```

Restore that saved path from the cache before evaluating a consumer that uses
`previousPlan = builtins.storePath savedPlanPath;`. Source selection remains
independent of the saved graph. An older or unrelated graph can be supplied;
its benefit depends on how many current recipes it shares.

The benchmark script supports `--after-previous-plan` for a paired comparison,
and `--previous-plan` to supply the same prior graph to both revisions. Exact
commands are in the JSON. For example:

```sh
python3 scripts/benchmark-ci.py --before /path/to/baseline --after /path/to/current \
  --source /path/to/upm --package ./cmd/upm --runs 7 \
  --module-cache /nix/store/your-module-cache \
  --after-previous-plan /nix/store/your-saved-plan-result.drv \
  --before-iets /nix/store/your-iets --after-iets /nix/store/your-iets \
  --nix-option sandbox true --nix-option sandbox-fallback false \
  --nix-option substituters '' --nix-option always-allow-substitutes false
```

## Validation

All nine platform/Go-version combinations preserve identical planner and result
derivations when the new argument is omitted. Local focused tests pass with
Go 1.25.12, 1.26.5 and 1.26.6 using Nix, and with Go 1.26.5 using nested static
iets. They check the public flake helper, unchanged source, embedded-file edits,
a new dependency, compact interfaces, content-addressed early cutoff, declared
planner inputs, and absence of the old plan root from the next plan's closure.
Invalid source still fails after a saved plan; a cached empty-test result still
requires semantic validation after source changes. iets also agrees with Nix on
outer derivation paths using one and four workers.

The new suite runs once per platform in the Go 1.26 compatibility jobs, and in
the iets validation script. The complete Linux amd64/arm64 and Apple Silicon
matrix remains the merge gate.
