# Reusing Go compilation during CLI checks, November 11, 2026

Nix builds the drvgo CLI and its tests with `-trimpath`. Two tests cleared
`GOFLAGS` before invoking Go, causing the standard library to be compiled again
without that option. The test helper now reads the test binary's embedded build
settings and retains only `-trimpath` when it was enabled. Other ambient Go flags
remain excluded. Ordinary untrimmed local tests keep their previous behavior.
Test cases, assertions, and vet remain enabled.

Baseline `2fa1fae` contains the direct script renderer; implementation `f309d5d`
changes test support and adds the bootstrap benchmark. Production CLI code,
package build settings, and worker recipes are unchanged. The subsequent report
commit adds documentation only. [Raw results and reproduction metadata](ci-round19-2026-11-11.json)
include individual trials, commands, hashes, validation, and cache experiments.

## Fresh CLI package builds

Seven alternating trials plus one warmup per revision use unique derivation
names to force a complete `nix/package.nix` build, including all unit tests and
vet. Each build has a fresh writable Go cache. The pinned Go 1.26.5 SDK and OS
filesystem caches are warm; remote substitution is disabled. Sandboxing is on,
sandbox fallback and IFD are off, with four Nix jobs and two cores per job.

| Median | Before | After |
|---|---:|---:|
| Evaluation | 0.240 s | 0.245 s |
| Realization, including tests and vet | 9.504 s | 6.293 s |
| Complete package build | 9.755 s | 6.535 s |

The complete build is **33.0% faster**, saving 3.220 seconds. This measures building
drvgo itself; it does not imply faster downstream compilation or evaluation.
Every one of the 16 builds has the same executable SHA-256, complete output NAR
hash, and runtime references. The NAR hash is
`84fd4793d7bdfec9698be4f3521c0341c50f978e3bc8f242d611e4c534530791`.

Reproduce with separate checkouts and the pinned nixpkgs source:

```sh
python3 scripts/benchmark-bootstrap.py \
  --before /path/to/baseline --after /path/to/current \
  --nixpkgs /path/to/pinned-nixpkgs --runs 7 --cores 2 --jobs 4 \
  --out /tmp/drvgo-bootstrap-results
```

The benchmark preserves logs, expressions, output hashes and references. Unique
names force new builds without deleting store paths or weakening sandboxing.
It does not time downloading the SDK, a cold OS page cache, or remote transfers.

## Dynamic CI and dependency size

Seven alternating trials plus warmups also rebuild the fixture's dynamic planner
with both nested Nix and static iets PR #3, revision
`69883a64bfb0d9a95dce253dae304878e07b076e`. The CLI and worker outputs are warm here.
The normal benchmark disables IFD, substitutions, iets tracing and compiled-file
caches, and iets fallback. Nested iets uses one worker. All 32 runs retain the
same final package output.

| Nested evaluator | Before | After |
|---|---:|---:|
| Nix | 0.854 s | 0.861 s |
| iets | 0.669 s | 0.663 s |

These differences are under 1%; treat downstream CI latency as unchanged.
Compiler, linker, native, and full worker toolchain derivation paths are identical.
The CLI's input-addressed output path and planning bundle path change because the
CLI source input now includes the test helper, despite identical executable bytes.
Including raw derivation metadata, planner inputs grow by **1,064 NAR bytes and
273 compressed bytes**, with no additional paths. The compression measurement is
a fresh local file cache using zstd level 3, not a network-transfer measurement.

| Planner | Paths | Before NAR bytes | After NAR bytes | Before zstd bytes | After zstd bytes |
|---|---:|---:|---:|---:|---:|
| Nix | 964 | 339,231,544 | 339,232,608 | 97,478,705 | 97,478,978 |
| iets | 909 | 235,726,952 | 235,728,016 | 61,776,450 | 61,776,723 |

Untrimmed local unit tests and vet pass. Separate metadata probes built with Go
1.25.12, 1.26.5, and 1.26.6 verify both trimmed and untrimmed binaries and confirm
that changing ambient `GOFLAGS` after compilation does not affect the helper.
The validation source and exact commands are in the JSON. Platform/SDK CI is a
separate merge gate; these local measurements were taken on x86-64 Linux.

## Separate standard-library cache experiments

Before changing test flags, prototypes copied a separately built stdlib cache
into each fresh CLI build. All preserved the installed NAR and runtime references.
Cache action timestamps were normalized after checking their format; independent
producers for the latter two variants yielded identical NAR hashes. No compiled
archive bytes were patched, and the immutable input cache was never modified.

| Prototype | Empty Go cache | Prebuilt cache available | Cache built in this run | Incremental zstd payload |
|---|---:|---:|---:|---:|
| CLI dependencies, trimmed | 9.619 s | 6.791 s | not timed together | 11.29 MB |
| CLI and test dependencies, trimmed | 9.653 s | 6.685 s | 10.390 s | 14.30 MB |
| Trimmed and untrimmed dependencies | 9.698 s | 3.867 s | 11.602 s | 29.97 MB |

These are three-trial medians plus warmups on the baseline code, including Nix
builds, tests, vet, and cache copying. They are separate runs from the seven-trial
comparison above. The last two use rotating order across all three conditions.
The compressed payload is the additional cache object alone; the Go SDK and its
existing dependencies are shared inputs. No network timing is claimed.

A narrower standalone CLI compilation probe fell from 4.448 s to 0.334 s when its
cache was already available, but producing that cache took 4.261 s and the probe
excluded Nix checks. This illustrates why a warm-cache result alone is insufficient.
The dual cache cuts a warm bootstrap substantially, but adds about 30 MB to fetch
and makes an uncached first build 19.6% slower. It is not enabled or exposed by
this change. Reusing the existing per-build cache through consistent test flags
improves the first build without adding a new downloadable cache artifact.
