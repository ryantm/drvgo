# Source-edit reuse and optional prepared modules

Measured on Linux amd64 with Go 1.26.5 on November 11, 2026. The baseline is
`d17c9d26521d39c3f3a84923a159f74101238022`, now included in main through PR #12.
The implementation is `e5de560` and `1151fdf`, with module preparation subsequently
made opt-in. [Raw samples and validation evidence](ci-round6-2026-11-11.json)
include the initial measurements, the final explicit opt-in comparison, and the
preparation/restoration probe scripts.

## Default improvement: application edits preserve dependency recipes

Go's dry run returns to the caller's directory between commands. drvgo previously
retained that directory's source snapshot in every action containing cgo or Go
assembly, even when the action belonged to a dependency. Changing the caller's
`main.go` therefore invalidated unrelated standard-library and native packages.

The exporter now preserves the caller's working directory only for native
packages actually located there. Dependencies retain their own native source
directories; absolute-input compiler and linker commands use the work directory.
This preserves root-package cgo/assembly support without attaching the
application's files to dependency recipes.

Five alternating trials of a 61-package, stdlib-only command, with an application
source edit before every build:

| Measurement | Before | After |
| --- | ---: | ---: |
| Evaluation + realization | 4.413 s | 1.038 s |
| Outer evaluation | 0.405 s | 0.396 s |
| Realization | 3.998 s | 0.628 s |
| Package builds per edit | 42 | 1 |

The full dynamic build is **76.5% faster** in this fixture. Tools and dependencies
are available, but every trial has a distinct application edit and output. Edits
use equal-length strings unique to each revision/trial, preventing the second
revision from reusing the first revision's newly built application. Each binary
is run and its output checked. Build counts deduplicate repeated daemon log lines.
Warmup is excluded; strict sandboxing and IFD-disabled planning remain enabled;
remote cache lookups are disabled equally on both sides. Builds use four jobs
and two cores per builder.

A separate 63-package external-cgo fixture changes 44 recipes before the fix and
only its application recipe afterward. Its regression test checks dependency
recipe equality after a source edit, including the external module with a
relative `#cgo CFLAGS: -I.` include path.

## Optional prepared modules

`prepareModules = true` converts the fixed module proxy into an immutable cache
once. The selected Go SDK validates and unpacks each module ZIP. The cache keeps
`.ziphash`, `.mod`, `.info`, and other metadata, including metadata-only module
versions, but removes duplicate ZIPs and locks. Discovery uses that cache offline.
An explicit `moduleCache` or CLI `-module-cache` can share an existing cache.

Five alternating trials on pinned UPM, 554 packages, with fresh planners and warm
tools, dependency cache, and compiled package outputs:

| Measurement | Fixed proxy per plan | Prepared cache reused |
| --- | ---: | ---: |
| Evaluation + realization | 3.442 s | 2.537 s |
| Outer evaluation | 0.417 s | 0.416 s |
| Realization | 3.024 s | 2.121 s |

This saves **26.3%** for this steady CI workload. The final comparison explicitly
passes `prepareModules = true` only to the new revision. Preparation is excluded
from these timings. Package outputs stay stable across trials within each mode;
the external cgo cache path changes automatic action IDs between modes.

| Dependency representation | ZIP proxy | Prepared cache |
| --- | ---: | ---: |
| NAR bytes | 190,596,720 | 1,007,179,880 |
| zstd level 3 cache bytes | 181,216,454 | 142,449,756 |
| Store paths | 1 | 1 |
| Local NAR decompression + restore | 0.111 s | 0.690 s |

The prepared cache transfers **21.4% fewer compressed bytes**, but expands to
**5.3 times the NAR size**. The earlier manually prepared cache and the automatic
builder produce the same NAR hash, so their measured transfer sizes are identical.
Restoration uses warm compressed input and fresh directories, five alternating
trials, excluding warmup. It includes decompression and file creation/writes,
but excludes network transfer, database registration, deletion, and an fsync
guarantee. These are local measurements, not remote-store download timings.

Fresh sandboxed cache preparation takes **7.284 s** of realization, or **7.685 s**
including outer evaluation, with the proxy, CLI, and SDK already available.
An ignored recipe nonce forces six actual preparations; five measured trials
exclude warmup and include Nix's output hashing and registration. All produce
the same cache path. Preparation covers all 113 proxy modules, including modules
outside the selected command's dependency set.

This first-use cost is why preparation remains **opt-in**. It suits CI that reuses
the cache or publishes it for later workers. The default keeps extracting from
the fixed proxy per plan; stdlib-only and vendored builds need no prepared cache.
The prepared output has no SDK/proxy references, is reused after source edits,
and is absent from the application's runtime closure. Go 1.25.12 and 1.26.5 produce
the identical UPM cache output. Workers still receive selected package snapshots.

The CLI closure grows by 100,672 NAR bytes and 31,226 zstd bytes. Worker toolchain
recipes are unchanged by this round. Removing unused source dependencies changes
affected package recipes once; subsequent application edits reuse them.

## Nix and iets

Already-exported UPM graph evaluation, 15 alternating measured trials:

| Evaluator | Before | After |
| --- | ---: | ---: |
| Nix | 135.8 ms | 134.3 ms |
| iets PR #3, one worker | 42.5 ms | 43.8 ms |
| iets PR #3, four workers | 57.7 ms | 59.5 ms |

Evaluation is essentially unchanged in this follow-up. The initial five-trial
sample had much higher four-worker variance (69 to 121 ms medians), prompting
the longer comparison; both datasets are retained. No fallback or tracing cache
is used. All evaluators produce the same derivation for each graph.

iets revision `69883a64bfb0d9a95dce253dae304878e07b076e` also passes outer and nested
dynamic builds using the prepared external-cgo cache under Go 1.25.12 and 1.26.5.
The existing direct-output, repeat-build, embedded-file, optional-test, and runtime
reference cases pass. Integration runs overlapped other correctness checks, so
their timings are not used as performance evidence.

## Validation and reproduction

Local validation includes unit tests and vet; the full Go 1.26.5 compatibility
suite; module-cache integration under all three supported Go versions; native
source-removal/reproducibility checks; sandboxed UPM builds; cache preparation
`--check` against the resolved CA recipe; source-edit reuse; matching standalone
and dynamic outputs; and rejection of a mismatched `go.sum`. The offline fixture
is part of every Linux amd64, Linux arm64, and Apple Silicon compatibility job.
No network access is needed by that fixture.

```sh
python3 scripts/benchmark-source-edit.py \
  --before /path/to/baseline-drvgo --after . --runs 5

python3 scripts/benchmark-ci.py \
  --before /path/to/baseline-drvgo --after . \
  --source /path/to/pinned-upm --package ./cmd/upm \
  --vendor-hash 'sha256-A4CU4C5SmEZP6Q+CVHjp+Jy4UxRXAnpvhzrsdq4NlsM=' \
  --after-prepare-modules --runs 5 \
  --nix-option always-allow-substitutes false --nix-option substituters '' \
  --nix-option sandbox true --nix-option sandbox-fallback false

python3 tests/module-cache.py \
  --toolchain "$tc" --drvgo bin/drvgo --flake-toolchain toolchain-go1_26 \
  --iets /nix/store/<iets-output>/bin/iets
```

UPM is pinned at `35a76c282507fb942445c0ee98427b3d1ef772bc`. The JSON includes
exact store paths, flags, individual samples, and the preparation/restoration
scripts; adjust their checkout/output paths when reproducing. Relative cgo flags
in an application's own relocated source remain a separate automatic-build-ID
identity issue. Sharing a prepared module cache addresses external module paths,
not that remaining case.
